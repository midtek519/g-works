How G-Vault supports FERPA compliance

Personal Version · Grades, G-Scope, Recommendations, and Integrity · Reviewed October 23, 2026 · Reference version 1.4

G-Vault separates Private AI from General AI by the information a feature needs. Private AI runs on this computer to help prevent unintended FERPA disclosures: protected records stay local, and AI processing of those records uses the local model. General AI handles blank teaching materials and approved text that the author has reviewed and redacted for sharing. It can use a connected ChatGPT account. A module may use both connections for different tasks.

The central rule: identifiable records stay in the private workspace. Any information shared outside it needs a permitted purpose, an appropriate recipient or service, and review of the exact material leaving the computer.

This document describes the current implementation and the responsibilities around it. It is an internal explanation, not a Rutgers approval or a legal certification of the app. Technical safeguards support compliance; they do not establish every user's authority to access or disclose a record.

1. What is protected, and where it lives

FERPA covers maintained records directly related to a student. Here that includes grades, linked course history, recommendation materials, and integrity case records. Protection also matters when a person can be identified through context rather than a name. See 34 CFR §99.3.

The default private workspace is Data\PrivateModules inside G-Vault. Course databases and letter/case libraries can also be opened from a folder you choose. It holds the module databases, person and case records, source documents, letter drafts, and local review artifacts. Supporting private renderers and signature resources are kept under Data\PrivateSource. Signed outputs, previews, recovery copies, and diagnostic logs can also contain protected information. They deserve the same protection as the original records.

Temporary files are separate from retained records. The Settings cleanup removes disposable compilation caches and previews only. It does not delete G-Scope projects or scans, private correspondence, saved revisions, recovery copies or published PDFs. Managed scan storage has its own deliberate cleanup workflow; scans may remain until they are no longer needed, subject to applicable retention requirements.

These folders are separate from the reusable teaching source in mh-git. The private module integration does not push them to Git or Overleaf. The G-Works installer supplies the reusable application framework with empty records. It excludes existing databases, correspondence, cases, signatures, personal settings, and approved writing examples. Sharing a whole working G-Vault folder would bypass that release boundary.

“Local” describes how the app stores and processes records. G-Vault does not check whether Windows, a backup agent, a mapped drive, or another program synchronizes those folders elsewhere. The actual storage and backup configuration still matters.

2. Safeguards built into the local app

  • Local connections. The shell and module services listen on 127.0.0.1, the computer's loopback interface. Opening a module connects the browser to a local service, rather than a hosted student-record site.
  • Browser request checks. Host and Origin checks limit requests to the expected local app. Changes require a per-process request token. The initial embedded module page also checks its parent and a launch nonce. These reduce unwanted access from other websites.
  • Restricted page behavior. Module content policies limit scripts and data connections to the module's own origin. Responses use Cache-Control: no-store and a no-referrer policy. The navigation bridge exchanges fixed view identifiers and request identifiers, not student records or letter bodies.
  • Local processing. Imports, database queries, document extraction, handoff preparation, and TeX compilation run locally. Protected-record AI requests use the configured local model through a literal loopback connection. General AI has separate, named routes for blank-exam work and approved redacted text briefs. Connecting a ChatGPT account does not change the private routes. Manual exports remain separate author actions.
  • Explicit decisions. Reviewing a brief, signing a final letter, confirming that an email was sent, and recording a case outcome are separate actions. Producing a PDF does not establish that it was sent or that a case should close.

These are browser and workflow safeguards. They are not a separate Windows account or an application login system. G-Vault does not encrypt the student-record databases or documents at rest; ChatGPT connection credentials are separately protected for the current Windows user. The modules run with the current user's filesystem permissions. Other software running as that user, browser extensions with access, or someone using an unlocked session may still reach information. Separate module services are logical boundaries, not operating-system sandboxes.

4. Private AI and General AI: what the names mean

Private AI: protected data stays on this computer

The purpose of Private AI is to help avoid unintended FERPA disclosures. Student scans, identities, grades, private correspondence and original evidence do not go to the general account connection. If a feature needs AI to process protected information, it uses the local model. “Private” describes the processing boundary; it is not a certification that every use complies with FERPA.

The connection accepts only literal loopback HTTP addresses, bypasses web proxies, rejects redirects, and rejects models reporting a remote host. An Ollama engine or a compatible local server can be configured in Settings → AI → Private AI. The local engine, model, computer security and storage must remain under the user's control. Changing the local engine to a remote/cloud forwarding service would defeat this boundary; do not do so.

General AI: academic sources and reviewed redacted text

General AI is for inputs suitable to share outside the private record workspace: blank exam questions, linked academic solution excerpts, rubric drafts from the blank exam, and approved redacted correspondence briefs. In Settings → AI → General AI, the author chooses the local connection or a ChatGPT account and selects an available model and thinking level. General tasks keep using the local connection until the author chooses and saves ChatGPT.

With ChatGPT selected, eligible inputs leave the computer and are processed by OpenAI using the connected ChatGPT plan. Sign-in and permission to use a plan do not authorize disclosure of student records. The app requests no tools, browsing, file access, conversation history or automatic source-folder access. Each request includes only the prepared input for that task. It uses the public Responses API with storage disabled and accepts a result only after a completed response. Windows protects this app's saved connection credentials for the current user; tokens are not sent to page scripts or borrowed from Codex.

The feature selects the route, not the module as a whole. G-Scope can use General AI to draft a rubric from the blank exam and Private AI to apply the reviewed rubric to student work. A redacted recommendation brief can use General AI; any direct analysis of private supporting material must remain local. General AI is never installed as the grading or identity-recognition callback.

Review the exact brief before sharing

Redaction is a review process, not a guarantee from a name-removal filter. Distinctive events, dates, handwriting, grades, quotations, institutions and combinations of facts can identify a person. An input that still identifies a student is not suitable for the general route. Remove those details before approval, or keep the task with Private AI. The app cannot prove that every identifying detail has been removed.

Choosing Draft with General AI checks the approved brief and its receipt before sending text. Returned wording remains an editable local draft. Use draft checks that the approved brief and original wording still match, then saves a draft marked for review. It does not sign, send, assign a grade, choose a finding or sanction, or complete a case step.

Redacted online handoff remains a manual alternative. It displays a copyable prompt that the author can review and paste into a permitted service. Copying or downloading does not send the prompt. Opening an external service does not validate the account or authorize disclosure. Do not upload entire private folders, receipt files or original evidence as part of that handoff.

Recommendation drafting briefs

The app replaces known names, aliases, identifiers, email addresses, and common phone-number patterns with placeholders. The author reviews and edits the exact brief before saving it as approved. Known subject identifiers still present in that text cause export to be rejected. Reviewed style examples may be included for voice, and selected grades or ranks may be included when requested.

A local receipt ties the approved text to its person and letter and records content hashes. Applying a returned draft checks that the brief and original letter body still match that receipt, then marks the new wording for review. Names are filled into the final document locally.

Integrity correspondence briefs

The correspondence brief replaces the case identifier and known party identifiers, then requires author review of the exact text. Its receipt also ties the brief to the communication and current case context. A returned draft is rejected if the approved context has changed and is left for local review when accepted.

Attachment authorization is a different boundary from anonymization. Recommendation and correspondence brief workflows can explicitly authorize selected original attachments. That permission identifies the files the assistant may read; it does not redact them or establish a FERPA exception. Original attachments and local receipts can contain identities, paths, or identifying metadata. Do not upload an entire Approved Briefs folder or treat its receipts as anonymous documents.

Integrity rationale handoff ZIPs

The separate rationale workflow prepares selected evidence and notes locally. It replaces known identifiers in extracted text and asks the author to review the text and every included PDF or image. The author draws redaction boxes over page images and approves the prepared copies. Those black regions replace pixels before a new PDF is created; the original PDF text layer, comments, attachments, and source metadata are not copied into it.

Export requires approved text, removal of the identifiers the tool recognizes, and matching hashes for all prepared page copies. The ZIP contains reviewed text, generic document names, prepared copies, instructions, and a manifest. It excludes the original evidence and local identity map. Uncovered handwriting, faces, distinctive events, dates, quotations, and other contextual clues can still identify a student. The software cannot establish that every identifier has been removed.

Local rationale drafting from reviewed evidence

The rationale review screen also offers Draft rationale with local Ollama. It uses the same text approval and prepared-copy checks as the existing ZIP export. The local reader verifies the approved text, manifest, and every included document hash, then reads only those prepared redacted copies. It does not substitute the original evidence or send the local identity map. Page observations produced by the model are unverified notes; the resulting rationale must be checked against the evidence. Copying that draft does not change a case finding, sanction, letter, signature, or sending status.

Exam batches and prepared suggestions

For grading, G-Scope sends one approved answer crop, its rubric, version-specific reviewed solution guidance, and any approved common-mistake decisions per model request. It does not send an entire exam PDF, cover pages, filenames, source paths, Gradescope URLs, or a student identity map. The crop still needs review: handwriting within an answer can contain identifying information. Batch proposals are stored locally with their source, rubric, crop and model references; corrections are separate human-review records.

G-Scope also keeps a reusable rubric library in its private module folder. Rubric Lens writes only the explicitly reviewed rubric title and text through the paired local connector when the user chooses Save to G-Scope; that action makes no AI request. Identical text is deduplicated. Renaming changes the library title, and deleting moves library files to local Trash while preserving copies already used by exams. Reusable reviewed question cards exclude version-specific solutions, crops and scan approvals. Sharing a rubric across exam versions preserves each version’s own solution guidance. The preview text still needs review for accidental identifying information.

Local identity recognition is a separate, explicit operation. The instructor marks and approves name, NetID and version regions on blank exam templates, and confirms PDF booklet boundaries. G-Scope sends those field crops only to the installed local model, then requires review before assigning an exam to a version. Names and NetIDs stay in the local archive; they are not added to question-grading prompts or structured Lens exports. A question region overlapping a marked name or NetID region is rejected. Names written elsewhere still require visual review.

Common-mistake discussions use the question, its rubric, and the instructor’s description. A proposed decision becomes reusable only after explicit approval. Matching decisions are shared across versions with the same rubric; version-specific worked solutions remain separate. Grading snapshots record the approved revisions. Conflicting matches, uncertain recognition and model disagreements are flagged. Consistency reports show recognized patterns and instructor overrides; they do not prove that the model recognized every mistake correctly. These saved rules are supplied context, not model training.

The suggestions JSON is private educational-record material even when it uses opaque exam IDs. Rubric Lens loads it into extension session storage and keeps submission links locally. Discard or closing Chrome clears the session data; the downloaded JSON and G-Scope database remain on disk. The extension supports individual links or instructor-confirmed ordered review for one question and tab. Ordered review requires checking the starting exam and that Gradescope’s next-student order matches the exported order without skipping or filtering. Each acceptance remains an explicit click. Accept and next verifies the rendered selected state and a uniquely identified next submission before navigating; this is not a server save acknowledgment. Unexpected navigation, ambiguity or a context change pauses the sequence.

Managed scan cleanup first lists the exact files and affected saved runs, then requires explicit deletion confirmation. It deletes selected scan bytes in G-Scope’s managed source/derived folders only. It retains local identities, source hashes, handouts, rubrics, proposals and reviews; it is not full record erasure. Original PDFs uploaded from other folders remain untouched. Missing scan files prevent fresh processing and make affected runs unavailable for current automatic export. Re-uploading the identical source can restore the managed copy. Rubric-library deletion remains separate and moves library entries to Trash.

What “anonymous” must mean in practice

Replacing names is only a starting point. FERPA's de-identification provision requires a reasonable determination that students cannot be identified, considering other reasonably available information and combined releases. A stable case code, an unusual achievement, an exact rank, or a small class can undermine that determination. See 34 CFR §99.31(b)(1).

Hashes verify whether content changed; they do not encrypt it, make it anonymous, or authorize disclosure. Approval checkboxes record the author's confirmation, not an independent legal review.

Use the current Rutgers data classification and AI matrix to check the service, institutional account, and data type. Service-specific approvals and conditions must be checked in that current matrix. This implementation update does not independently re-establish a provider approval. ChatGPT sign-in verifies that connection’s account identity and the fixed OpenAI service endpoint; it does not verify Rutgers approval or the suitability of an input. Manual handoff destinations and accounts remain the author’s responsibility. A personal subscription or Rutgers email address alone does not establish the required institutional protections.

5. Responsibilities outside the app

Keep the Windows account and device protected, lock the session when away, and use institutionally appropriate storage, device encryption, backups, and access permissions. This review did not assess those settings. Keep private records out of public repositories, shared development bundles, unapproved sync folders, and screenshots used for troubleshooting.

Before sharing, identify the purpose and recipient, select only the necessary records, and review the actual outgoing files. A “download,” “copy,” “prepare email,” or “open output folder” action changes how easily a file can be shared; it does not make it public or authorize its release. Review recipient addresses and attachments in the approved delivery system before sending.

Rutgers requires written student permission for a recommendation that uses grades, GPA, or other education-record information. When consent is the disclosure basis, it must identify the records, purpose, and recipient or recipient class and be signed and dated. A recommendation inspection waiver is distinct from permission to disclose records. The app does not collect or validate FERPA consent. See Rutgers recommendation guidance and the Department of Education consent requirements.

Follow institutional retention, access, correction, and disclosure-record requirements. Local revisions and hash receipts help trace particular actions but are not a complete FERPA disclosure log or a tamper-proof audit system. The app does not enforce a university retention schedule, legal hold, or student-access request process. Do not delete records while an applicable access request or preservation obligation is pending. See 34 CFR §§99.10, 99.20, and 99.32.

For uncertainty about authority, storage approval, an AI destination, or an accidental disclosure, contact the appropriate Rutgers privacy or IT office. The Rutgers FERPA information page provides current contact information.

6. A short explanation to share

G-Vault keeps protected student records in a private local workspace. Private AI processes those records on the same computer to help prevent unintended FERPA disclosures. General AI handles blank teaching materials and approved redacted briefs; a connected ChatGPT account may process those eligible inputs online. Features select the route, so a module can use both connections without sending its student records to General AI. The author reviews outgoing redacted text and returned drafts. Grades, findings, sanctions, signatures and sending remain explicit human actions. These safeguards support FERPA obligations alongside appropriate authority, device security, retention and institutional policy.
